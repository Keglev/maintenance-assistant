2. v1.2.0 — TRUST CHAIN
   - APPROVE WORKFLOW, per ADR-006's dated note (2026-08-10): the
     Techniker writes and never edits his own; the Schichtleiter edits
     and forwards; the Admin approves, and may close after an edit.
     AUTHOR AND APPROVER ARE NEVER THE SAME PERSON — four-eyes where
     it bites, at the moment a protocol becomes citable. The approval
     state then gives search a NEW FACET for approved protocols, for
     free.
   - DUPLICATE DETECTION ON APPROVAL: run the existing pgvector
     similarity against the same machine's protocols; high similarity
     raises a WARNING with links and NEVER BLOCKS. The E-47 seed is
     the proof case — same code, four different root causes, all
     legitimate, and any threshold useful enough to catch a real
     duplicate would flag those four as copies of each other. The
     admin decides join / keep / delete.
   - ADR-006 gets a revision on implementation; migrations expected.

   THREE DESIGN DECISIONS, DECIDED BY CARLOS 2026-08-11, TO BE
   IMPLEMENTED IN v1.2 — none of them is built yet. They are written
   down here so v1.2's implementer inherits the reasoning and does not
   re-open settled ground:

   (1) APPROVAL IS A STATUS, AND UNAPPROVED PROTOCOLS STAY
       SEARCHABLE. In Carlos's words: the admin may not review at a
       weekend, and the factory does not stop. Hiding an unapproved
       protocol until someone signs it off would mean the newest
       knowledge — the protocol written about the fault happening
       right now — is exactly the knowledge retrieval cannot see.
       THE TRADE-OFF IS EXPLICIT AND ACCEPTED: an unapproved protocol
       is less reliable to troubleshoot from. It follows that the UI
       MUST MAKE APPROVAL STATE VISIBLE on the answer and on its
       sources, and never silently — an unapproved source cited
       without a mark would be the NFR-2 discipline working against
       itself, making an unreviewed claim look as checked as a
       reviewed one.
   (2) THE 150 SEEDED PROTOCOLS ARE BORN APPROVED. A new Flyway
       migration adds ~15 UNAPPROVED protocols on top, so the admin
       has a real approval queue to demonstrate rather than an empty
       one. The new protocols lean toward EASIER faults — machine does
       not start, machine stops without warning — which also
       broadens a corpus that is currently specialist-heavy.
   (3) TECHNIKER MAY WRITE, NEVER EDIT — not even his own protocol.
       A correction is REQUESTED from the Schichtleiter, who performs
       it. Author is never the corrector; corrector is never the
       approver. This is the four-eyes rule applied twice rather than
       once, and it is what makes the chain a chain.

THE SWAGGER ENTRY POINT TOOK THREE ROUNDS, and the reason is worth
carrying forward. #30 fixed GET /swagger-ui (302 -> the UI, confirmed
live). A `curl -sI` afterwards still answered 401, which looked like
the same bug and was not: -I sends HEAD, the permit list matched
HttpMethod.GET only, and HEAD is a method of its own to the matcher —
so EVERY public path, /api/health included, refused HEAD while serving
a browser perfectly. Any uptime probe using HEAD would have seen a
permanently unauthorised health check. Closed in fix/swagger-entrypoint
together with two neighbours of the same defect: /swagger-ui/ and the
old /swagger-ui.html now redirect into the UI, and the ERROR dispatch
is permitted so that a permitted-but-unmapped path answers 404 instead
of a misleading 401 (measured both ways in a real container).
THE LESSON, next to the #26 one: MockMvc could not see any of this. It
does not distinguish HEAD the way the matcher does and performs no
error dispatch, so the guard tests passed twice while production
refused. The replacement runs on RANDOM_PORT against a real Tomcat with
the JDK HTTP client, following no redirects.

  answer is in the DOM in both states, never truncated and never split, because

  EXPANDS FIRST and then points at its card: a marker answering a click with

  DIALOGS: stored protocol text one step up (new --t-md token; monospace stays

- FOOTER SERVER-HEALTH DOT 2026-08-11 (feat/footer-health-dot), the last code
  PR before v1.1.0. GET /api/health (public, unchanged) every 60 s WHILE SIGNED
  IN only, with a 5 s client-side timeout so a hanging backend reads as offline
  rather than as forever-pending. Three states, and the dot ALWAYS carries its
  own label — a status told only in colour is one some readers do not get, the
  same rule NFR-2 follows.
  IT IS A COMPONENT, NOT A SERVICE, and the reason is its lifetime: the footer

  ONE FAILURE FLIPS IT. No hysteresis, no backoff, no reconnect banner: a

- EDIT + ARCHIVE 2026-08-10 (feat/edit-and-delete-archive). TWO DECISIONS FROM
  ADR-006 WERE REVERSED, and the revision is APPENDED to the ADR rather than
  rewritten into it — the original text stands, the way the ARM entry in
  DECISIONS.txt stands.
  (1) EDITING IS ALLOWED NOW. The argument against it was that an answer cites a
  protocol as it stood when the answer was produced. THAT ARGUMENT ASSUMED
  ANSWERS ARE STORED, and they are not: every answer is generated per query and
  every citation resolves live. There is no answer table, no answer history and
  no shareable answer URL, so the exposure is not everything the system has ever
  said — it is the answers currently open on a screen. THAT RESIDUAL IS REAL AND
  IS WRITTEN DOWN rather than explained away; what makes it acceptable is that
  an edit replaces a wrong Massnahme with a right one, is attributed with a
  mandatory comment, and RE-INDEXES. Re-indexing is a CONDITION of the flow, not
  a step in it: an edit that left the old chunks would be worse than no edit,
  because retrieval would keep matching text the document no longer contains.
  MACHINE AND TYPE ARE NOT EDITABLE, and a request that tries is refused 400
  (PROTOCOL_IDENTITY_LOCKED), never silently ignored — a client told 200 would
  report a move that did not happen. The rule in one line: WORDS CAN BE FIXED,
  IDENTITY CANNOT. Editing an archived protocol is 409, not 404: the same admin
  can read it in the archive one tab over, so "no such protocol" would be a lie
  their own screen contradicts.
  (2) DELETION IS NOW AN ARCHIVE. #37's hard delete removed the bad protocol AND
  the evidence that it ever existed, which is the one thing the insider-threat
  chain cannot lose — it was missing its last link, PRESERVE. The chunks are
  still deleted (instant removal from every answer, every role), deleted_at is
  set, the row and the file stay, and a moderation_event records actor + comment.
  NO RESTORE, BY DESIGN — no endpoint, no flag, and a test that fails if a route
  named restore/undelete appears. Capped at 50 per machine; past that the oldest
  are purged completely, enforced SYNCHRONOUSLY by the delete that breached the
  cap (a retention job is a scheduler that can silently stop running).
  THE ADR'S OWN OBJECTION TO SOFT DELETE IS ANSWERED, not ignored: it said soft
  delete makes every query grow a filter it must never forget, and that a
  forgotten filter makes a deleted protocol citable again. The answer is that
  RETRIEVAL IS PROTECTED BY THERE BEING NOTHING TO RETRIEVE. The deleted_at
  guards on the row-based reads are the second line, and what they prevent is a
  deleted protocol showing up in a LIST — visible and harmless — rather than in
  a green Mode A answer.
  READ-PATH AUDIT (all guarded): retrieval, the corpus list, Meine Uploads, the
  live document endpoints, the indexer's load and the backlog enqueue. THE LAST
  TWO ARE THE DANGEROUS ONES — either would have rebuilt an archived protocol's
  chunks and put it back into search, which is the only way a soft delete could
  be undone.
  moderation_event has NO FOREIGN KEY to protocol, deliberately: a cascade would
  mean the 51st deletion erasing the record of the first.
  NOTE FOR THE NEXT SESSION: the migration is V4 and runs through the normal
  Flyway path on deploy — no manual step, unlike a compose or Caddy change.
  STILL OPEN from ADR-006, unchanged: draft/approve, four-eyes deletion,
  automated suspicion signals. Four-eyes is now a BIGGER gap than it was, because
  the single admin account can change what the corpus says and not only remove
  from it.

UNIFIED REQUIRED CHECK — "build-and-test"
Branch protection requires exactly ONE status check name:

    build-and-test

Three workflows gate pull requests, and all three name their job
`build-and-test` (job id, no `name:` key — the id is what GitHub reports).
Whichever part of the repo a PR touches, a job under that name reports on
it. A PR touching two areas gets two checks under the name; both must pass.

The pull_request path lists are a PARTITION and are maintained as a set:

    frontend-ci.yml    paths:        frontend/**
                                     .github/workflows/frontend-ci.yml
    docs-pr-check.yml  paths:        docs/**
                                     .github/workflows/docs.yml
                                     .github/workflows/docs-pr-check.yml
    backend-ci.yml     paths-ignore: frontend/**
                                     docs/**
                                     .github/workflows/docs.yml
                       => catch-all: backend/**, docker/**, spike/**,
                          README.md, .gitignore, AI-USAGE.md, LICENSE,
                          everything else

INVARIANT — do not break this:
- A path may be ignored by backend-ci.yml ONLY if another workflow gives
  that PR a build-and-test check. A path ignored by all three leaves its
  PRs with no required check and permanently unmergeable.
- Root files (README.md, .gitignore, AI-USAGE.md, LICENSE) stay with
  backend-ci on purpose: they live outside docs/, so the docs build never
  reads them and would gate them on nothing.
- The gate workflows' own files (frontend-ci.yml, docs-pr-check.yml) are
  deliberately NOT ignored by backend-ci.yml, so editing a gate runs the
  backend suite too. Getting these lists wrong is how the repo loses its
  ability to merge.
- push triggers are NOT a partition: they exist to produce artifacts and
  fire the deploy workflows, so they stay narrow (backend-ci on
  backend/**, frontend-ci on frontend/**). Widening them would publish a
  new image for a README typo.

PIPELINE ARCHITECTURE (.github/workflows/)
1. frontend-ci.yml    PR (paths frontend/**) + push main: job
                      build-and-test — test with coverage (test runner:
                      vitest in jsdom — no browser needed on the runner),
                      build; upload coverage + Compodoc artifacts on main
2. backend-ci.yml     PR (catch-all, see partition above) + push main
                      (paths backend/**): job build-and-test — mvn verify
                      (JUnit + JaCoCo), OpenAPI spec; upload artifacts
                      on main
2b. docs-pr-check.yml PR (paths docs/** + the docs workflow files): job
                      build-and-test — renders the mermaid diagrams, builds
                      the site with build-docs.sh and link-checks it with
                      lychee. Publishes nothing.
3. frontend-deploy.yml / backend-deploy.yml
                      workflow_run success of the matching CI on main,
                      or manual workflow_dispatch for a redeploy without
                      a code change. Two jobs:
                        image  - multi-arch docker build (amd64+arm64)
                                 -> GHCR, tags :latest and :sha-<commit>
                        deploy - ssh to the Hetzner host as the deploy
                                 user, `compose pull <svc> && up -d <svc>`,
                                 then verify over the PUBLIC url (so DNS,
                                 TLS and Caddy are exercised too) and fail
                                 the job if it does not come back healthy
                      Both deploy jobs share the concurrency group
                      "hetzner-deploy" with cancel-in-progress: false, so
                      rollouts to the server serialise and a superseded
                      build never cancels one in flight.
                      Secrets (repo level): DEPLOY_SSH_KEY, DEPLOY_HOST,
                      DEPLOY_USER. The key is a dedicated ed25519 pair
                      used by CI only; it is passed through the step env,
                      never interpolated into a command line, and removed
                      in an always() step.
4. docs.yml           a) push main paths docs/**: regenerate mermaid
                         diagrams, build the site with Pandoc via
                         .github/scripts/docs/build-docs.sh -> gh-pages
                         (theme: docs/_theme, landing + arc42 + ADRs)
                      b) workflow_run success of frontend-ci/backend-ci:
                         publish coverage + API docs into gh-pages
                         subfolders (/frontend/coverage, /frontend/
                         api-docs, /backend/coverage, /backend/api-docs)
                         WITHOUT deleting the rest (keep_files)
5. release.yml        tag v*: GitHub Release with generated notes
