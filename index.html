Maintenance knowledge, findable in plain language

A technician on the shop floor types what the machine is doing, in German or in English, and reads back an answer with the protocols it was taken from — each one citable and openable. When no protocol matches, the system says so and shows no sources at all.

Live at maintenance.smartsupply.com.de. Four demo accounts — operator, techniker, schichtleiter, admin — are printed on the sign-in page together with the password they share. The role decides what an answer contains.

Project overview

What it is

Maintenance knowledge in manufacturing sits in scattered PDFs, scans and paper manuals, and in the heads of experienced technicians. Many machines here run fifteen to twenty years on PLC or SCADA only, so the machine itself offers little beyond an error code. This system indexes maintenance protocols and answers questions about them in natural language, with citations — and it is explicitly not a ticketing or CMMS system. The overview is the short way in; requirements holds the user stories and the seven non-functional requirements.

No real customer or plant document is used anywhere in this project. The corpus is generated, which the standing statement on the data says in as many words, along with the two consequences it has for every measurement below.

Where it comes from

The rules this system obeys are not retrieval defaults. They come from maintenance work in US and German plants, and each one is written down where it was decided rather than only implemented.

  • An Operator and a Techniker get different answers to the same question. An Operator receives only actions they may perform — clean a sensor, remove material, load a program — and is told to escalate when the fix needs a Fachkraft. Filtering happens server-side, on the token's role. Requirements, US-1 · ADR-003
  • Only a Schichtleiter may write. Reading is broad and writing is one role, for quality and consistency. A Schichtleiter can nevertheless upload arbitrary text, so uploads carry a moderation and approval chain, and an unapproved source is marked in the answer that cites it. DECISIONS.txt · ADR-006
  • An error code is what the machine gives you, and it is nearly all it gives you. It is also the worst kind of input for a vector search: five characters a technician reads off a display carry certainty and almost no meaning. Measured — “Was bedeutet KOM-04?” retrieved the right protocol at rank 1 scoring 0.4288 against a 0.55 gate, so the reader was told nothing while the answer sat at the top of the list. The fix grounds on the literal term instead of moving the gate. ADR-009

How it was built

One Spring Boot application, internally split into ingestion, query and web, with an Angular client in front of it and three containers behind it. Retrieval is one SQL statement combining the machine filter with cosine ranking over the chunk table, which is why the vectors live in PostgreSQL rather than in a separate vector database. arc42 · ADR-001 · ADR-004

The working method is stated rather than implied, because a reader is owed the difference between what was written and what was generated:

  1. A chat model is a sparring partner while the design documents and decision records are written — it challenges the decisions, it does not make them.
  2. An editor agent implements against those documents as the source of truth, and reports its deviations in the pull request rather than smoothing them over.
  3. Every pull request is read line by line before merge, a red pipeline blocks it, and anything the browser does is verified in a browser.

The full account, session by session, including the defects that were found only by running the thing — is in AI-USAGE.md.

How it is verifiable

Every claim above has somewhere to be checked, and the reports below are generated by the pipelines rather than written by hand.

  • Eleven decision records, each dated, each carrying the alternatives it rejected and the evidence it was decided on. The ADR index
  • Coverage, published per run. Backend 92% of instructions and 86% of branches (JaCoCo); frontend 97.44% of statements, 88.38% of branches, 96.16% of functions and 97.4% of lines (Vitest). Behind them: 274 backend unit tests, 262 integration tests against Testcontainers, 321 Vitest specs and 39 Playwright cases against a real Keycloak and a real backend, plus 18 screenshot baselines compared per run.
  • The API as it is served, not as it is described. The REST reference is rendered from the OpenAPI document the application produces, and the live Swagger UI sends requests against the running deployment.
  • The working ledger is published, not summarised. Every phase, every survey finding and every correction, including the ones that turned out wrong. PROJECT-PHASES.txt
  • The retrieval thresholds and the reranker were measured, not chosen. A ratified set of 19 questions is run against the real provider and the real index; the 0.55 gate was kept on a sweep that showed it, and the reranker was dropped because recall@1 was already 16/17 and the one failing question was at rank 1 already — nothing for a reranker to reorder. ADR-008 · ADR-009

What to see in two minutes

Sign in at maintenance.smartsupply.com.de as techniker; the password is on the sign-in page.

  1. Pick Presse 3 (PR-03) and click an example question. Four suggestions appear under the question box in the interface language. Clicking one fills the box and does not submit — you still read the question and still press Ask, so what you learn is the shape of a question that works. The answer arrives with its sources as cards you can open. ADR-011 · the questions themselves
  2. Switch the interface to EN, pick Kompressor 1 (KP-01), and ask in German: “Kompressor schaltet nach einer halben Stunde wegen zu hoher Temperatur ab”. The protocol behind that fault is written in English. There is no translation step anywhere — one embedding model holds both languages in one space. This is case G10 of the ratified measurement set. the golden questions
  3. Stay on Kompressor 1 and ask “sensor fehler”. None of its 14 protocols is about a sensor. The answer comes back as a general suggestion, labelled ungrounded, with no source area at all — and it says how many protocols the machine does have, so the emptiness is a fact rather than a shrug. the corpus · the two answer modes
