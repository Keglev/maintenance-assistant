   PROGRESS 2026-08-14 — PR 4 of 4 IS OPEN (feat/duplicate-detection),
   THE LAST FEATURE OF v1.2.0. Approving a protocol first asks what the
   corpus already says: up to three protocols on the SAME machine that
   say close to the same thing, each with its date, its similarity as a
   whole percentage and — the field the decision turns on — ITS OWN
   APPROVAL STATE. "Nearly the same as something an administrator
   already vouched for" is a merge-or-reject question; "nearly the same
   as one nobody has reviewed" is often two honest accounts of one
   fault, and this corpus wants both. Each opens in the existing
   read-only viewer, because a percentage is not a comparison.
   IT WARNS AND NEVER BLOCKS. No branch anywhere refuses an approval on
   a score, the approve button is never disabled, a FAILED similarity
   call approves anyway (the backend recomputes and records regardless),
   and a test approves past a verbatim copy so that nobody adds the
   "obvious" guard later. THE DIALOG OPENS ONLY WHEN IT HAS CONTENT —
   nothing similar is still one click, and a permanently empty section
   is one readers learn to skip, including on the day it fills.
   WHAT IS COMPARED: the PROTOCOL, as the centroid of its chunk
   vectors. Chunk-to-chunk best match was measured beside it and
   rejected — a maximum over a set that GROWS WITH DOCUMENT LENGTH
   cannot go down when material the other document lacks is added, so it
   flags two long protocols overlapping in one paragraph. Measured: E-47
   #1 against #13 is 0.8205 by chunk-max and 0.7698 by centroid, and
   that gap is the false positive's exact shape.
   THE THRESHOLD IS A CONFIG PROPERTY, MEASURED, and it is NOT ADR-002's
   0.55 — that is question-to-chunk, this is document-to-document
   between two texts of one genre on one machine from one template. The
   MEAN over all 1,393 same-machine pairs is 0.5547.
   THE FINDING, AND IT IS NOT WHAT THE BRIEF ASSUMED: the E-47 four are
   the tightest FAULT cluster (0.7594-0.8329) and they are NOT the
   constraint — they clear the threshold by 0.09. The highest legitimate
   pair in the whole corpus is PR-07's Halbjahreswartung and
   Jahreswartung at 0.9151: scheduled maintenance shares a template, a
   technician and a vocabulary, and two filled-in checklists resemble
   each other more than two incidents do. A realistic duplicate (one
   incident re-narrated by a second person) scores 0.9305 and a verbatim
   re-file 0.9778, so the usable window is 0.0154 WIDE. 0.92 sits in it,
   low on purpose. THE NARROW WINDOW IS SURVIVABLE ONLY BECAUSE IT
   WARNS: a false positive costs one card an approver dismisses, a false

   (e) THE SINGLE STAGED PUBLISH — a sketch, not a design
     WHAT KEEP_FILES ACTUALLY BUYS, so the replacement keeps it: four
     independent producers write four disjoint subtrees, and only one
     of them exists on any given run. The site job has no coverage; a
     backend run has no frontend tree. keep_files is what stops each
     publish deleting the three trees it did not build. It costs the
     ability to delete anything, ever — C2 is that cost, paid twice.

     THE SHAPE THAT KEEPS BOTH: make the publish a function of ONE
     staged tree rather than four partial ones.

       1. Every producer keeps uploading its artifact exactly as today.
          Nothing about backend-ci, frontend-ci or the site build
          changes; this is a change to the publisher alone.
       2. One publish job, triggered by any of the three, begins by
          CHECKING OUT gh-pages into a staging directory. That is the
          step that does not exist today, and it is the whole idea: the
          published site becomes an input to the publish rather than a
          thing the publish half-overwrites.
       3. It replaces, wholesale, only the subtrees this run rebuilt —
          rm -rf the destination, then copy — and leaves the others as
          checked out. A rename now deletes, because the site tree is
          replaced rather than merged into.
       4. keep_files: false, publishing the staged tree. The four trees
          survive because they are IN the staged tree, not because the
          publisher was told not to delete.

     WHAT THIS MUST NOT BREAK, and each is a real hazard:
       - The .nojekyll file at the root is not produced by any build.
         Under keep_files it survives by luck. A staged publish must
         write it deliberately or the site stops serving underscore
         paths.
       - The concurrency group must stay `gh-pages` with
         cancel-in-progress: false, and it becomes MORE load-bearing,
         not less: a checkout-modify-publish cycle has a window a plain
         overwrite does not.
       - The first run under this scheme deletes six files (C2). That
         is the point, and it should be a deliberate first run with the
         diff read, not a side effect of merging the change.
       - Whether LICENSE and README.md at the site root should exist at
         all is a content question this sketch does not answer — it only
         makes the answer enforceable.
     NO PREDICTED OUTCOME NUMBERS: this is a shape, and the PR that
     builds it measures what it actually publishes.

- EDIT + ARCHIVE 2026-08-10 (feat/edit-and-delete-archive). TWO DECISIONS FROM
  ADR-006 WERE REVERSED, and the revision is APPENDED to the ADR rather than
  rewritten into it — the original text stands, the way the ARM entry in
  DECISIONS.txt stands.
  (1) EDITING IS ALLOWED NOW. The argument against it was that an answer cites a
  protocol as it stood when the answer was produced. THAT ARGUMENT ASSUMED
  ANSWERS ARE STORED, and they are not: every answer is generated per query and
  every citation resolves live. There is no answer table, no answer history and
  no shareable answer URL, so the exposure is not everything the system has ever
  said — it is the answers currently open on a screen. THAT RESIDUAL IS REAL AND
  IS WRITTEN DOWN rather than explained away; what makes it acceptable is that
  an edit replaces a wrong Massnahme with a right one, is attributed with a
  mandatory comment, and RE-INDEXES. Re-indexing is a CONDITION of the flow, not
  a step in it: an edit that left the old chunks would be worse than no edit,
  because retrieval would keep matching text the document no longer contains.
  MACHINE AND TYPE ARE NOT EDITABLE, and a request that tries is refused 400
  (PROTOCOL_IDENTITY_LOCKED), never silently ignored — a client told 200 would
  report a move that did not happen. The rule in one line: WORDS CAN BE FIXED,
  IDENTITY CANNOT. Editing an archived protocol is 409, not 404: the same admin
  can read it in the archive one tab over, so "no such protocol" would be a lie
  their own screen contradicts.
  (2) DELETION IS NOW AN ARCHIVE. #37's hard delete removed the bad protocol AND
  the evidence that it ever existed, which is the one thing the insider-threat
  chain cannot lose — it was missing its last link, PRESERVE. The chunks are
  still deleted (instant removal from every answer, every role), deleted_at is
  set, the row and the file stay, and a moderation_event records actor + comment.
  NO RESTORE, BY DESIGN — no endpoint, no flag, and a test that fails if a route
  named restore/undelete appears. Capped at 50 per machine; past that the oldest
  are purged completely, enforced SYNCHRONOUSLY by the delete that breached the
  cap (a retention job is a scheduler that can silently stop running).
  THE ADR'S OWN OBJECTION TO SOFT DELETE IS ANSWERED, not ignored: it said soft
  delete makes every query grow a filter it must never forget, and that a
  forgotten filter makes a deleted protocol citable again. The answer is that
  RETRIEVAL IS PROTECTED BY THERE BEING NOTHING TO RETRIEVE. The deleted_at
  guards on the row-based reads are the second line, and what they prevent is a
  deleted protocol showing up in a LIST — visible and harmless — rather than in
  a green Mode A answer.
  READ-PATH AUDIT (all guarded): retrieval, the corpus list, Meine Uploads, the
  live document endpoints, the indexer's load and the backlog enqueue. THE LAST
  TWO ARE THE DANGEROUS ONES — either would have rebuilt an archived protocol's
  chunks and put it back into search, which is the only way a soft delete could
  be undone.
  moderation_event has NO FOREIGN KEY to protocol, deliberately: a cascade would
  mean the 51st deletion erasing the record of the first.
  NOTE FOR THE NEXT SESSION: the migration is V4 and runs through the normal
  Flyway path on deploy — no manual step, unlike a compose or Caddy change.

  automated suspicion signals. Four-eyes is now a BIGGER gap than it was, because
  the single admin account can change what the corpus says and not only remove

      - THREAT SPLIT (this is the ADR's spine): (a) malware on the
        user's machine can also steal cookies, keylog the password and
        read the screen — NO web-app architecture defends against a
        compromised endpoint; state this plainly rather than pretend.
        (b) XSS stealing the token from the SPA IS in scope and has
        real, proportionate mitigations.
      - What is ALREADY in place (record, don't rebuild): access token
        lives in sessionStorage (tab-scoped, gone on close — the
        angular-oauth2-oidc default; NOT localStorage), lifetime is
        15 min (measured: expires_in 900), Angular templates escape by
        default and the answer renderer uses typed segments with no
        innerHTML anywhere (verified in review of #25).
      - CHEAP AND REAL, do it: security headers at the Caddy layer —
        Content-Security-Policy (script-src 'self'; connect-src self +
        auth host; frame-ancestors 'none'), X-Content-Type-Options
        (backend already sends nosniff — align the frontend),
        Referrer-Policy, Permissions-Policy. NOTE: Caddyfile changes
        deploy like compose changes — BY HAND on the host (ops rule).
        Verify the CSP does not break the OIDC redirect or the blob:

      - DISPROPORTIONATE FOR A PORTFOLIO DEMO, decide + document in

        (backend-for-frontend holding tokens server-side, HttpOnly
        session cookie to the browser) is the textbook answer to

        second auth code path to a demo whose token already dies in
        15 minutes. Decide: keep the public-client SPA + short TTL +

        the demo users hold no data worth stealing (synthetic corpus).

UNIFIED REQUIRED CHECK — "build-and-test"
Branch protection requires exactly ONE status check name:

    build-and-test

Three workflows gate pull requests, and all three name their job
`build-and-test` (job id, no `name:` key — the id is what GitHub reports).
Whichever part of the repo a PR touches, a job under that name reports on
it. A PR touching two areas gets two checks under the name; both must pass.

The pull_request path lists are a PARTITION and are maintained as a set:

    frontend-ci.yml    paths:        frontend/**
                                     .github/workflows/frontend-ci.yml
    docs-pr-check.yml  paths:        docs/**
                                     .github/workflows/docs.yml
                                     .github/workflows/docs-pr-check.yml
    backend-ci.yml     paths-ignore: frontend/**
                                     docs/**
                                     .github/workflows/docs.yml
                       => catch-all: backend/**, docker/**, spike/**,
                          README.md, .gitignore, AI-USAGE.md, LICENSE,
                          everything else

INVARIANT — do not break this:
- A path may be ignored by backend-ci.yml ONLY if another workflow gives
  that PR a build-and-test check. A path ignored by all three leaves its
  PRs with no required check and permanently unmergeable.
- Root files (README.md, .gitignore, AI-USAGE.md, LICENSE) stay with
  backend-ci on purpose: they live outside docs/, so the docs build never
  reads them and would gate them on nothing.
- The gate workflows' own files (frontend-ci.yml, docs-pr-check.yml) are
  deliberately NOT ignored by backend-ci.yml, so editing a gate runs the
  backend suite too. Getting these lists wrong is how the repo loses its
  ability to merge.
- push triggers are NOT a partition: they exist to produce artifacts and
  fire the deploy workflows, so they stay narrow (backend-ci on
  backend/**, frontend-ci on frontend/**). Widening them would publish a
  new image for a README typo.
