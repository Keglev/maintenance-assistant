PROJECT DECISIONS — Instandhaltungs-Assistent / Maintenance Protocol Assistant
Status: v1.3.0 released; refactor phase (read-only survey), 2026-08-21
(Details in: REQUIREMENTS.md v0.2, DOMAIN-MODEL.md, adr/ADR-001..004, ARCHITECTURE-RATIONALE.md)

== PRODUCT ==
- Domain: industrial maintenance (Instandhaltung), NOT procurement (already 2 repos there)
- Problem: maintenance knowledge trapped in PDFs/scans/paper + heads; night shift without
  technician; faults re-diagnosed although solved last month
- NOT a ticketing/CMMS system; escalation chain is context only
- Roles: Operator (operator-safe answers only) / Techniker (full answers) /
  Schichtleiter (sole write access: create + upload protocols) / Admin (Keycloak IT role, AND
  since 2026-08-10 the corpus moderator: reads and deletes any protocol — ADR-006)
- Write access restricted to Schichtleiter: quality + consistency + anti-garbage.
  Known limitation (documented): fixer != documenter, depends on shift handover.
- Two answer modes, visually distinct (anti-hallucination):
  Mode A "Belegte Antwort" = grounded, every claim cited
  Mode B "Allgemeiner Vorschlag - keine Quelle im Bestand" = labeled ungrounded troubleshooting;
  operators get operator-safe steps + escalation advice only
- Corpus: ~150 synthetic protocols (Claude-generated, documented in AI-USAGE.md),
  ~70% DE / 30% EN, quality mix incl. messy ones; demo seeds: E-47 on Presse 3 (3x),
  one Mode-B gap, one DE-query->EN-protocol match
- NO translation anywhere: texts stored as written; multilingual embeddings bridge DE<->EN
- Search scope Phase 1: exact machine only ("similar machines" = Phase 2 candidate)
- Protocol types: STOERUNG | WARTUNG (INSPEKTION dropped - lives in manufacturer manuals)
- UI: bilingual DE/EN, 3 views (search, upload, login via Keycloak redirect)

== ARCHITECTURE (see ADRs) ==
- ADR-001: modular monolith first (packages: ingestion/query/web), Spring events for async;
  Phase 2: extract ingestion service + Kafka. 3 containers Phase 1: app, Postgres+pgvector, Keycloak
- ADR-002 (ACCEPTED 2026-08-06, decided on the measured spike in spike/adr-002/): IONOS AI Model
  Hub primary, Nebius Token Factory documented fallback. Multilingual embedding model is a HARD
  requirement; IONOS serves three, Nebius exactly one public (single point of failure) and no
  bge-m3 - that reversed the proposal. Also: better cross-language retrieval (-0.011 vs -0.033
  penalty), Berlin (de-txl) vs Helsinki, EUR pricing, and the identical Llama-3.3-70B inside the
  NFR-4 30s ceiling (median ~11s) where Nebius breached it.
  Embeddings: BAAI/bge-m3, 1024 dims -> pgvector column is vector(1024).
  Chat: meta-llama/Llama-3.3-70B-Instruct (quality) + Qwen/Qwen3.5-9B (fast); per-role choice in
  Phase 3 against the production prompt.
  Similarity threshold = CONFIG PROPERTY, initial 0.583, revalidate against the real corpus.
  Provider swap stays a config change (OpenAI-compatible), with 3 caveats: IONOS needs an explicit
  encoding_format (gateway 500s on the SDK default base64), ignore the *-migration model aliases,
  Qwen3.5-9B needs reasoning_effort="none" or it returns empty content.
  RESIDUAL RISK: no provider-side hard spending cap - IONOS has cost alerts only, EUR 7 alert
  configured. NFR-7 therefore rests on the application layer as designed; worst-case abuse is
  measured in cents. Latency figures are indicative (small sample, residential connection) -
  revalidate from the production host in Phase 3. 0.583 is bge-m3-specific, re-tune on any
  embedding model change. The few-shot citation prompt must exclude the Mode-B/refusal path
  (observed leakage: a citation appended to a refusal).
  Citation compliance and answer language are prompt/app concerns, verified enforceable:
  few-shot example + language pinning reached 100%, structured JSON as the app-side enforcement.
- ADR-003: Keycloak as IdP. Angular: Auth Code Flow + PKCE; backend: OAuth2 Resource Server.
  "Keycloak vs OAuth2" is a category error: OAuth2/OIDC = protocols, Keycloak = implementation.
  Realm config exported + versioned (realm-export.json)
- DEMO LOGIN (2026-08-08, feat/shopfloor-ux, under ADR-003): the landing page offers one button per
  demo user that starts the NORMAL Auth Code + PKCE redirect with login_hint=<username>, so Keycloak
  prefills the field and the visitor types only the shared password. FULL ONE-CLICK LOGIN WAS
  CONSIDERED AND REJECTED, both ways of doing it. (a) The password grant (ROPC / Direct Access
  Grants) would have to be enabled on the demo client, which exposes the realm's token endpoint to
  password spraying against EVERY user in it — a public demo password turns that from a theoretical
  weakness into an invitation, and the blast radius is the whole realm rather than the one account
  the visitor was offered. (b) A Keycloak login theme that autofills the credentials is a
  hand-deployed artifact on a host where CI deploys images only (== PRODUCTION OPERATIONS ==),
  bought for a purely cosmetic gain. login_hint keeps the standard flow completely intact, costs one
  query parameter, and the password never passes through the application. The demo box also states
  the boundary out loud — isolated realm, synthetic data only, rate-limited, 15-minute sessions — so
  the public password reads as a designed demo boundary rather than a leftover credential.
- NO DOCUMENT-LANGUAGE FIELD ON UPLOAD (2026-08-10, feat/upload-parity-and-settings). The dropdown
  is REMOVED from the form and the frontend stops sending the parameter. RETRIEVAL IS
  LANGUAGE-AGNOSTIC BY ARCHITECTURE and always was: bge-m3 embeds DE and EN into ONE vector space
  (ADR-002 — the cross-language demo, DE question against the EN FB-04 protocol, exists precisely to
  prove it), and the answer language is pinned to the QUESTION's language in the prompt, never to
  the document's. The protocol.language column is stored metadata with NO retrieval role, so the
  field asked the Schichtleiter to classify their own prose and nothing read the answer — and a
  wrong answer to it would have been invisible, which is worse than no answer. The upload endpoint
  already declares the parameter optional (required=false), so this is a frontend-only removal with
  NO backend change: seeded protocols keep their language values, user-created ones store none.
  If a language ever earns a retrieval role, DETECT it from the text rather than ask.
- UPLOAD GUARDS (2026-08-10, sec/upload-guards). Four limits on the write path, all configuration
  properties: multipart size stated explicitly (256KB file / 512KB request — Boot's implicit 1MB was
  never a decision anyone made), content validation before anything is stored (empty / not .txt /
  NUL byte in the first 8KB), and 10 uploads per minute per user with 429 + Retry-After. A refused
  upload leaves NO row and NO file, which is what keeps the moderation backlog to content that was
  accepted on purpose. .md IS NO LONGER ACCEPTED: it was a developer convenience from when writing
  a file was the only way in, and typed entry replaced it — one fewer route for a file nobody
  intended. The per-user bucket is IN MEMORY and is not the real ceiling; the daily embedding budget
  in Postgres is, because it is durable and shared. THE NUMBERS BEHIND ALL OF THIS are in arc42 §11.1
  "Upload abuse, quantified" — a saturating attacker costs well under a cent a day and needs decades
  to fill the disk, which is why these guards are proportionate rather than defensive.
  MEASURED, NOT REASONED, and both surprised: a controller-local @ExceptionHandler never sees
  MaxUploadSizeExceededException (thrown before a handler is resolved — it must be @ControllerAdvice),
  and that exception's getMaxUploadSize() returns -1, so the 413 message states the configured
  property instead. Also: an UNAUTHENTICATED oversized upload answers 401, not 413 — the security
  filter chain runs before multipart parsing.
- ADR-004: pgvector inside Postgres, no dedicated vector DB. Relational filter + vector ranking
  in ONE query; one backup; no cross-store consistency problem. Scale ceiling documented.
- Stack: Java 21, Spring Boot 4.1 (3.x is EOL since 2026-06-30), Angular + TypeScript (thin),
  PostgreSQL + pgvector, Keycloak, Docker Compose, GitHub Actions, Hetzner VPS
- Spring AI: CLOSED 2026-08-07 -> plain RestClient. Measured in spike/spring-ai-boot4/ (RESULTS.md).
  Spring AI 2.0.0 (first generation on Spring Framework 7) IS compatible with Boot 4.1 - it
  auto-configured and produced 1024-dim vectors from IONOS. It is declined on proportion, not on
  compatibility, and the spike says so plainly rather than pretending it did not work:
    * what we need is one POST /v1/embeddings; that is ~40 lines of RestClient
    * the starter pulls the OpenAI Java SDK, OkHttp, Kotlin stdlib, azure-identity, a template
      engine, chat-client/chat-memory/tool-calling autoconfig - none of it used here
    * both failures hit in the spike happened BECAUSE the client assumes real OpenAI: base-url
      needs /v1 (changed between Spring AI generations) and it defaults to base64, which is the
      exact ADR-002 caveat. Our provider is OpenAI-COMPATIBLE, not OpenAI, permanently.
    * dimension assert, batching, retry, budget counter and token logging sit outside the call
      either way
  ADR-002 predicted this ("a Spring AI client can trip over it, a plain RestClient sending JSON
  floats will not") and the prediction was correct - measured, not guessed.
  The embedding call sits behind a narrow EmbeddingClient interface, so adopting Spring AI for the
  Phase 3 CHAT path (where advisors/tool-calling actually earn their weight) is a second
  implementation, not a rewrite. Carry forward: base-url must include /v1, and
  encoding-format: float must be set explicitly or IONOS returns 500.
- Boot 4.1 ships JACKSON 3 (tools.jackson.databind) as the message-converter default while Jackson
  2 is still on the classpath via other libraries. Asking a RestClient for a com.fasterxml
  JsonNode therefore fails at runtime. Found by running it: the first live corpus run failed all
  150 protocols on it. Use typed records for provider responses - they bind under either.

== INGESTION (Phase 2, 2026-08-07) ==
- Pipeline: upload -> file to volume -> RECEIVED row -> Spring event -> worker pool -> chunk ->
  embed -> chunks written -> INDEXED. Any failure -> FAILED + stored reason, row AND file kept.
  The event carries only a protocol id: that is the ADR-001 Kafka seam, and an id means one source
  of truth either side of it.
- Upload returns 202, not 201. The protocol exists but is not searchable yet (NFR-4).
- The transaction deliberately does NOT span the embedding call - a slow provider would otherwise
  hold a pooled connection the web layer needs.
- Chunking: PARAGRAPH-based, not fixed-width windows. These documents are short (many are a few
  sentences) and their paragraphs ARE the labelled sections (Symptom / Ursache / Massnahme); a
  fixed window cuts across exactly the boundaries an answer needs whole. Small sections are merged
  up to ~900 chars so a two-line protocol stays ONE chunk instead of four weak fragments; an
  oversized section splits on sentence ends with 150 chars overlap. Every chunk is prefixed with
  "<machine> - <error code> - <title>" so a retrieved chunk still says what it is about once it is
  separated from its row. Measured result on the real corpus: 150 protocols -> 166 chunks
  (134 protocols = 1 chunk, 16 = 2). CANONICAL as of the 2026-08-07 production run — an earlier
  151/167 figure was off by one (likely a leftover local test upload); 134x1 + 16x2 = 166 and
  production token counts matched local exactly. That ratio is the point: short documents.
- Re-indexing is delete-then-write per protocol, so the catch-up path and any retry are idempotent.
- NFR-7 for ingestion = a GLOBAL daily embedding-call counter in Postgres (table embedding_budget),
  not per-user limiting: ingestion is background load, so the shape of abuse is a re-index storm,
  not one person clicking. Per-user rate limiting belongs to the query path in Phase 3.
  The counter is incremented by the CLIENT as each request is served, not by the caller on success
  - the first live run made 150 paid calls that a caller-side counter never saw because every one
  of them failed while parsing the response.
- Measured cost of embedding the whole corpus: 150 calls, 27713 input tokens, EUR 0.00055.
  Cents was the estimate; hundredths of a cent is the measurement.
- Spring Modulith: optional upgrade, enforces ADR-001 module boundaries with tests

== PRODUCTION OPERATIONS (learned 2026-08-07, ops session) ==
- CI deploys IMAGES ONLY. docker-compose.prod.yml and .env.prod on the host are NEVER touched by
  the pipeline; merged changes to them must be applied on the server by hand (with a .bak copy)
  before or with the next deploy. #22 was merged in git and absent on the host until done manually.
- An .env.prod edit is INERT until `up -d --force-recreate <svc>` — environment freezes at
  container creation. Verified painfully: a correct key in the file, a stale one in the container.
- Production state: 150 INDEXED / 0 FAILED, 166 chunks (1024 dims), 150 documents on the volume,
  E-47 retrieval verified live, flags disarmed, nightly backups carrying real content (752K dump
  incl. vectors, pg_restore-verified). Full-corpus embedding measured: EUR 0.00055 / 52 s.
- LLM_API_KEY: 365-day token (exp 2027-08-07) in server .env.prod + password manager ONLY.
  Rotation ~2 weeks before expiry. Working paste path: Notepad (visual check) -> scp -> tr -d
  '\r\n' into the file -> verify (dots=2, ~1712 chars, eyJ prefix). Terminal-paste tricks caused
  a doubled+truncated 4095-char value twice; do not use them for this.
- 4xx from the provider is terminal, no retry (designed); rejected requests are not billed —
  two full 401 rounds cost EUR 0.00. The budget counter counts at the CLIENT as served, so failed
  parses still count (the caller-side version missed 150 paid calls on the first live run).
- Java base package: com.keglevich.maintenanceassistant — DECIDED 2026-08-07: KEEP. Chosen by
  convention from the owner's name; a rename (e.g. io.github.keglev) would touch every file for
  zero functional gain and muddy blame/history mid-project. Robots must not rename it.
- LLM_CHAT_MODEL in prod compose is live with an empty default (NOT commented, despite #22's
  summary) — same empty-override pattern #22 fixed elsewhere; fix lands with the Phase 3 chat
  default. arc42 debts (compose-sync rule -> 07, recreate rule -> §7.4) also land in that PR.

== QUERY PATH (Phase 3, 2026-08-07) ==
- Chat call: PLAIN RESTCLIENT, same proportionality reasoning as the embedding closure. Spring AI
  was deferred to here on the argument that advisors/chat-memory/tool-calling would earn their
  weight on the chat path. Built, they do not: there is no conversation to remember (every question
  is answered from the retrieved chunks alone), no tool to call, and the one advisor-shaped concern
  - citation enforcement - has to be checked against THIS query's retrieved chunks, which no
  framework can know. One POST /v1/chat/completions behind a narrow ChatClient interface, provider
  is OpenAI-COMPATIBLE not OpenAI, typed records for responses (Jackson 3 rule holds).
- Threshold 0.55, MEASURED against the real corpus through the production path, not the spike:
  E-47 0.6896 (Mode A), DE->EN 0.5566 (Mode A), Mode-B gap 0.4563 (Mode B). ADR-002's 0.583 would
  still have refused the cross-language demo. THE CROSS-LANGUAGE MARGIN IS 0.0066 - re-measure it
  first after any change to chunking, corpus or embedding model.
- CHAT MODEL: Llama-3.3-70B-Instruct FOR EVERY ROLE. No per-role split - the evidence does not ask
  for one. Qwen3.5-9B was measured worse on the production prompt in the way that matters: it
  failed to ground the cross-language case at all (14 completion tokens, no usable claim), so the
  app's citation validation correctly fell it through to Mode B and the demo would have shown "no
  source in the corpus". It also fragments (48 claims where Llama uses 11) and is therefore not
  even faster - the spike's ~3 s was a one-line refusal. Stays a config swap; the client sends
  reasoning_effort="none" for Qwen3.5 from the model id, not from a flag.
- TWO PROMPTS, NOT ONE WITH A FLAG. The citation few-shot cannot reach the Mode B path because it
  is not in that file, and Mode B's schema has no source field, so a leaked citation is a shape the
  provider will not emit. Mode B does carry a SHAPE example (no source/label/protocol in it) -
  measured necessary: without one, constrained decoding emitted the opening brace and then spent
  the whole output budget on whitespace, twice, at two caps. Raising the cap cannot fix that; the
  answer was never getting longer, only later.
- Citations are per PROTOCOL, not per chunk: chunk is the search unit, protocol is the citation
  unit. On the E-47 demo the top 5 chunks come from 4 protocols, and labelling per chunk cited one
  of them twice as if it were two independent pieces of evidence.
- Three layers enforce the citation rule and only the last does not depend on the model: few-shot
  example, JSON schema in which an uncited claim is unrepresentable, and validation against the
  chunks this query retrieved. A Mode A answer whose claims all fail validation falls through to
  Mode B - retrieval thought it had an answer, generation could not ground one, and the honest
  output is the labelled suggestion rather than an empty Mode A.
- max_tokens 1200, not the spike's 400: that was measured on a one-line refusal, and a
  claim-per-statement answer over four protocols is 481 tokens. Still runaway protection.
- NFR-7 query guards: Bucket4j ~10/min per user keyed by JWT sub (in memory - one instance, and the
  guard that must survive a restart is the daily counter, which is in Postgres); chat_budget table
  SEPARATE from embedding_budget so a re-index storm cannot exhaust the day's answers; max_tokens
  attached in the client so no prompt can forget it; Caffeine cache keyed by (normalized question,
  machineId, ROLE) - the role is in the key because an operator served from a technician's entry
  would get repair steps, which is a safety bug that is invisible in testing. Cache checked BEFORE
  the budget: a hit costs no provider call, so it must cost no budget.
- Role comes from the token, never from the request: it decides what the answer may contain.
  admin has no query access - it is a Keycloak IT role with no maintenance question to ask.
- LATENCY: RESIDUAL RISK CLOSED 2026-08-07. Measured three ways — residential through the query
  module, provider leg from the Hetzner host, end-to-end through production — and all three show
  the same shape, which attributes the variance to PROVIDER QUEUEING and not to any network path
  (identical request, identical token counts, 12.9 s vs 24.5 s minutes apart). Provider leg from
  the host, 8 forced ~500-token calls: median ~15 s (8.4-29.7). End-to-end through production, 5
  cold questions: median 5.5 s (4.5-17.2), the 17.2 s being the E-47 four-protocol answer. Real
  answers are far shorter than the forced probe, so end-to-end beats the provider leg. NFR-4 met
  at the median AND at the worst observed. The 38.9 s outlier stays possible on a bad queue day
  (shared serverless, no SLA at this tier): documented residual, no action — the mitigations are
  the client timeout, the "still working" state in the UI and the max_tokens cap.

== UI (Phase 3, 2026-08-08) ==
- The two answer modes are rendered as two visually distinct blocks, and that is a REQUIREMENT and
  not styling: NFR-2 makes the distinction the anti-hallucination mechanism. Mode A green with a
  check, inline [P1] markers linking into a source list. Mode B amber, hatched top edge, badge
  "Allgemeiner Vorschlag — keine Quelle im Bestand", and NO SOURCE AREA AT ALL — not an empty one,
  because an empty "Quellen" heading invites the reader to assume the sources are merely missing.
  The difference is carried by badge text, border weight and icon as well as by hue, so it survives
  monochrome and colour blindness.
- The client RENDERS the answer and does not re-read it: the backend already validated every
  citation against what it retrieved, so the only client-side parsing is splitting [Pn] markers to
  link them. A marker with no matching citation stays plain text — inventing a link would be the
  client asserting something the server did not.
- DE/EN is a RUNTIME DICTIONARY, not Angular build-time i18n. Two locales = two builds, two images
  and a routing decision, and it would make the language a property of the URL rather than of the
  person: switching would reload the page and lose the answer on screen. Two typed dictionaries
  mean a key added to one and forgotten in the other is a compile error.
- UI LANGUAGE IS INDEPENDENT OF ANSWER LANGUAGE. The backend pins every answer to the QUESTION's
  language and nothing is translated anywhere (== PRODUCT ==), so an English interface still shows
  a German answer, and the answer element carries its own lang attribute.
- Upload view is honest about the 202: status list with the FAILURE REASON, refreshed by a button.
  No polling loop — indexing takes seconds and a poll would run for as long as the tab is open to
  answer "still the same".
- PROTOCOLS OPEN IN AN IN-APP VIEWER (2026-08-08), superseding #26's blob: tab. The document is
  still fetched through HttpClient — a browser-followed navigation carries no Bearer token — but it
  is now RENDERED HERE instead of handed to the browser as an object URL in a new tab. The token
  problem only existed because the document left the application; keeping it here removes the
  category rather than working around it. It also fixes the experience the #26 fix created: the raw
  text viewer, outside the app, on a shop-floor tablet where tab switching is impractical. Parsing
  is defensive and produces TYPED SEGMENTS, never innerHTML — same rule as the answer renderer, and
  it matters more here because a Schichtleiter can upload arbitrary text. Anything unrecognisable
  falls back to the raw file preformatted; the dialog is never blank. Download is the only object
  URL left in the application.
- Role gating in the UI is presentation, never protection (NFR-3): the upload link and route are
  hidden from non-Schichtleiter so nobody is shown a door that opens onto a 403, and the backend
  refuses it regardless.

== BROWSER SECURITY / TOKEN HANDLING (Phase 4, 2026-08-08, ADR-005) ==
- THE THREAT SPLIT IS THE DECISION. (a) Malware on the user's machine is OUT OF SCOPE for this and
  for every web application: it reads HttpOnly cookies from the browser's own store, logs the
  password and reads the screen. Say so plainly instead of implying a defence. (b) XSS reading the
  token out of the SPA IS in scope and is what everything below addresses.
- PUBLIC CLIENT STAYS. Access token in sessionStorage (tab-scoped, the angular-oauth2-oidc default
  — NOT localStorage; the only localStorage key in the app is the DE/EN preference), lifetime 15
  min (realm accessTokenLifespan 900), Code Flow + PKCE S256, no implicit, no direct grants. The
  15-minute lifetime is the ceiling on what a stolen token is worth, and it is doing more work than
  any header.
- BFF (backend-for-frontend, tokens server-side, HttpOnly session cookie) is the RIGHT answer in an
  enterprise and is REJECTED HERE: it adds a stateful session store, CSRF handling on every mutating
  request, a second auth-code path and one more service on a two-vCPU host — to protect a token that
  expires in 15 minutes and reads a synthetic corpus. Documented as the production-grade evolution.
  This is interview material; the ADR is the long answer.
- SECURITY HEADERS LIVE AT CADDY, not in the frontend image: one place covers the SPA, the API and
  the OpenAPI UI, and the image stays environment-agnostic. CSP (script-src 'self'; connect-src self
  + the Keycloak host, which the discovery document and token endpoint need; frame-ancestors 'none'),
  X-Frame-Options, nosniff, Referrer-Policy, Permissions-Policy, HSTS without includeSubDomains and
  without preload (other subdomains of the domain belong to other projects).
- KEYCLOAK'S HOSTNAME KEEPS ITS OWN CSP. Overriding a policy written for an application we do not
  maintain is how a login page stops rendering.
- style-src KEEPS 'unsafe-inline' BY DECISION: Angular injects component styles as <style> elements
  at runtime and the only alternative is a per-request nonce (ngCspNonce), which a statically served
  bundle behind a reverse proxy cannot produce. Residual risk is CSS injection, not script execution.
- ANGULAR'S CRITICAL-CSS INLINING BREAKS A STRICT CSP: it emits <link ... onload="this.media='all'">,
  an inline event handler, and the page renders UNSTYLED when script-src refuses it. Production
  builds set optimization.styles.inlineCritical=false. Cost: one small render-blocking stylesheet.
- RECORDED, NOT FIXED: refresh-token rotation is off in the realm (revokeRefreshToken default), and
  the SPA neither uses silent refresh nor calls refreshToken(), so the session simply ends. No token
  binding / DPoP.
- THE CADDYFILE DEPLOYS BY HAND like docker-compose.prod.yml (== PRODUCTION OPERATIONS ==). CI pulls
  images only, so this hardening is INERT until someone copies the file and runs `caddy reload`.
  Verify with `curl -sSI https://<host>/ | grep -i content-security-policy`, then click through in a
  browser: a CSP breaks things the browser does itself, which curl never sees (the #26 lesson).

== DATA MODEL ==
- 3 entities: MACHINE -> PROTOCOL -> CHUNK (chunk = search unit, protocol = citation unit,
  machine = filter unit)
- Users NOT in DB (Keycloak claims only; uploaded_by = username string)
- Original files on Docker volume, path in DB (no BLOBs)
- CHUNK carries denormalized machine_id + error_code for one-query filtered vector search
- error_code = free text (real plants: mixed catalogs; code sometimes points to wrong problem
  -> semantic search on symptom text is the actual retrieval path, code only a hint)
- status lifecycle: RECEIVED -> INDEXED / FAILED (this transition = Phase 2 Kafka events)

== COSTS & OPERATIONS ==
- Monthly: VPS ~EUR 10-17 (~95% of cost) + LLM API ~EUR 1-3 (~5%). Corpus size is a non-cost:
  embedding all 150 docs < EUR 0.01 once; per-query cost independent of corpus size.
  Decision: KEEP 150 docs (richer demo), do not shrink corpus to save money.
- VPS cost reduction levers + caveats:
  1. ARM (Hetzner CAX): cheapest 8GB; caveat: arm64 images (all our images exist) +
     multi-arch CI build. DECIDED: yes, go ARM.
     REVISED 2026-08-06: deployed on CX33 (x86_64, 4 vCPU, 8GB) instead. Two reasons:
     the ARM price advantage disappeared in Hetzner's 2026-06 price restructuring,
     and CAX was out of stock at order time. CI keeps building amd64+arm64, so the
     images still run on ARM and moving back is a server swap, not a code change.
     Nothing in the stack depends on the architecture.
     REVISED AGAIN 2026-08-10: THE arm64 BUILD IS REMOVED; both deploy workflows build
     linux/amd64 only. The arm64 image had no consumer — production is x86_64 and the
     ARM price advantage is gone (see the 2026-08-06 revision above) — and it was being
     produced by qemu emulation on an amd64 runner, which is slow and not merely slow:
     on 2026-08-10 the FRONTEND deploy hung 13+ minutes in the arm64 leg and died with
     "qemu: uncaught target signal 4 (Illegal instruction)" during `npm ci`. Node under
     qemu is a known failure mode. Removing the leg roughly halves deploy wall clock and
     deletes that whole crash class. THE COST OF THE DECISION, stated: the published
     images no longer run on ARM, so "moving back is a server swap" is no longer true —
     it is a server swap PLUS restoring one line in each workflow (or, better, adding a
     native arm64 runner rather than emulating one). That is a one-line change, which is
     why it is not worth carrying a broken build to preserve.
  2. Shrink to 4GB: EUR ~5 saved; caveat: OOM risk during indexing (= broken-demo risk),
     Kafka Phase 2 won't fit. DECIDED: no, stay 8GB.
  3. Pause = snapshot -> DELETE server (stopped server still bills fully at Hetzner!);
     snapshot costs cents. Caveats: IP changes on recreate (use DNS/domain), NEVER down
     while applications are in flight. DECIDED: pay during application phases, snapshot only
     in real pauses.
- Token abuse protection = NFR-7, three layers:
  1. Provider: prepaid credit / spending limits (hard ceiling; verify in spike)
  2. App: Bucket4j rate limit per user (~10/min), global daily budget counter in Postgres
     (~200 calls/day, graceful message), capped max_tokens, cache for repeated queries
  3. Visibility: daily token usage logging
  Worst case math: 1000 spam queries = few EUR, not hundreds. Risk = surprise, not ruin.

== RETRIEVAL QUALITY, RATIFIED (v1.3.0, 2026-08-20) ==
- GOLDEN SET RATIFIED (#67): all 19 expectations ruled KEEP by Carlos, ratified:true with
  ratifiedBy/ratifiedOn once at the top level — ONE act ratified the set, not nineteen. Nothing was
  re-expected: 0 substantive changes, 5 notes extended, verified field by field. THE METRICS NOW
  REST ON OWNER-RATIFIED EXPECTATIONS; every recall figure quoted before this was measured against
  a set the same agent had written and graded. ADR-008 moves to Accepted.
- THE HARNESS ASSERTION IS FLIPPED, NOT DELETED: it required ratified:false — the guard against a
  robot marking its own homework — and now requires ratified:true, so a question added later is
  caught as a PROPOSAL before the aggregates can quote it. A set half proposal and half ruling
  reports one number for two kinds of claim.
- TWO STANDING CONDITIONS, written into the data rather than left in a session's head: G16 FLIPS to
  a Mode A case IN THE SAME PR that seeds Einlagerung protocols, or the harness reports a correct
  answer as a failure; and G19 stays single-answer, because "bleibt stehen" (was running) and "geht
  nicht an" (never started) are DIFFERENT MACHINE STATES — an operator may confuse them, the
  benchmark must not, or it can no longer tell a system that understands the distinction from one
  that does not.
- What ratification did NOT settle: 19 questions over 165 synthetic protocols still measure
  DIRECTION, not quality, and the set can still be over-fitted to.
- QUERY THRESHOLD STAYS 0.55 (#66, Carlos 2026-08-19). The sweep is FLAT from 0.48 to 0.55 —
  identical grounded counts, zero wrongly-grounded Mode B questions on every row — so moving it
  inside the plateau changes nothing observable and would only cost the number its measured
  history. THE FLOOR IS MEASURED AND NAMED so nobody optimises toward it: at 0.46-0.47 one Mode B
  question acquires a citation and at 0.45 and below both do, which makes 0.48 the floor of NFR-2's
  guarantee on this corpus. The one argument for lowering it (G13 at 0.4288) was REMOVED by #65's
  term override, not accommodated. Known thin spot unchanged: EN->DE clears 0.55 by 0.0082, and the
  response is measurement on every harness run, not a preemptive nudge.
- THE HELP PANEL IS PART OF RETRIEVAL'S CONTRACT WITH THE READER (#69), so A CHANGE TO LexicalTerms
  IS A CHANGE TO THE PANEL. It taught that a single word cannot be matched — true when retrieval was
  semantic only, untrue since ADR-009 — and nothing was red, because prose does not fail a build when
  the system underneath it changes. The panel now states the rule the code implements (a term needs
  at least one LETTER and one DIGIT to be matched literally, which is why "E-47" and "SV0410" work
  alone and "frei", "Druck" and "Band" do not), and TWO vitest specs pin BOTH halves: a panel that
  mentioned codes and dropped the generic-word half would teach the opposite error.
- QUERY COMPLETENESS-GATING REJECTED (Carlos, #69 drill) and NOT TO BE RE-PROPOSED: "e-47" is a lazy
  query that WORKS and "was bedeutet" is a lazy query Mode B already handles gracefully, so a
  completeness check would block the good one to prevent the harmless one.

== REFACTOR PHASE (2026-08-20) ==
- SURVEY FIRST, FIX SECOND (#70). The review is READ-ONLY and produces findings tables that fix
  nothing — SIX ORDERED PARTS (test coverage, code structure, config and root files, dead and
  redundant code, comments against the standards, and DOCS AUDITED LAST), enumerated canonically in
  PROJECT-PHASES.txt step 4 under CORRECTION 2026-08-21; the count and the detail live there and not
  here, so the two cannot drift again. Real refactors found there become their own small PRs rather
  than riding along with the review. ZERO BEHAVIOUR CHANGE. A refactor that starts with an edit is a
  preference; one that starts with a measurement is maintenance.
- THE STANDARDS ARE IN THE REPO BEFORE THE FIRST FIX PR OPENS, so "what good looks like" is
  reviewable rather than remembered. docs/REFACTOR-STANDARDS.txt is NORMATIVE — bands, counting
  methods, test conduct, coverage targets and the waiver register, and the single place any of them
  is edited. docs/refactor-standards.md is the published page and repeats none of the tables, so the
  two cannot drift.
- WAIVERS ARE GRANTED BY THE OWNER, NEVER ASSUMED, and the register was created EMPTY on purpose so
  the first waiver has somewhere to go instead of becoming a comment nobody collected.
- COVERAGE TARGET 85% on statements, branches (INCLUDING missed branches) and functions, BOTH
  STACKS, and THE FIGURE THAT COUNTS IS THE ONE CI PUBLISHES — a local run is a working tool, not
  evidence. It follows that KEY-GATED ITs COVER NOTHING: CI skips them for want of LLM_API_KEY, so
  code whose only tests are gated is uncovered however green it looks on a laptop with the key set.
- ENFORCEMENT IS A RATCHET, ARMED ONLY ONCE THE TARGETS ARE MET — jacoco check and vitest thresholds
  at the achieved numbers, so a regression fails the build. Authored in #70's standards file and
  ratified by its merge. Arming it first would only break CI; today neither stack enforces anything,
  which is why 85% is written down as a target rather than left to read as a gate.
