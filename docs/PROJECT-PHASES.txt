TWO CORRECTIONS TO THE RUNBOOK WORDING, both found by doing it:
  - THE CADDYFILE IS AT caddy/Caddyfile, not at the project root. Every
    earlier checklist wrote the path as if it sat beside the compose
    file.
  - `restart: unless-stopped` DOES NOT BRING BACK A CONTAINER THAT NO
    LONGER EXISTS. After `compose down` the containers are removed, so
    the restart policy has nothing to act on and the stack does NOT come
    back by itself on reboot. `compose up -d` is therefore a STEP OF
    EVERY WINDOW, not a finding and not a contingency. The earlier
    entry's "the stack comes back on its own" is true only of a reboot
    taken WITHOUT a `compose down` first.

copies carry their SOURCE's mtime (18:13-18:19, from the hand-deploy
earlier that day) rather than the time of the window.
A NAMING TRAP FOUND WHILE VERIFYING THEM, recorded so the next operator

BACKUP NAMING, 2026-08-27 ~20:40 UTC, root. The trap above was acted on
the same evening. Inventory taken first, because a naming rule written
without counting what is on disk is a guess:
  TWELVE backup files in /opt/maintenance-assistant, in FIVE naming
  formats — .bak (1), .bak-YYYY-MM-DD (2), .bak-YYYYMMDD-HHMMSS (3),
  .bak.YYYY-MM-DD (3) and, from this session, .bak.of-YYYY-MM-DD (3).
  Five formats on one host is what a convention nobody wrote down
  produces, and the published runbooks were themselves prescribing
  three of them.
THE THREE MIS-DATED FILES WERE RENAMED, not copied, with `mv -n`:
  .env.prod.bak-2026-08-27              -> .env.prod.bak.of-2026-08-19
  docker-compose.prod.yml.bak-2026-08-27 -> ....bak.of-2026-08-11
  caddy/Caddyfile.bak-2026-08-27        -> ....bak.of-2026-08-08
Each new name now agrees with its own mtime, which is the property the
old names could not have and the reason the rule reads the mtime rather
than the clock. Verified read-only afterwards, name against
`date -r`: eleven of twelve dated names match.
ONE ROOT-OWNED BACKUP WAS HANDED OVER in the same pass:
docker-compose.prod.yml.bak-20260807-193625 was root:root and is now
deploy:deploy. That is the #120 ownership class in miniature — a file a
root session created and did not chown, sitting unnoticed until somebody
enumerated the directory. It cost nothing this time because a backup is
never written to; the same omission on the compose file itself cost a
root console mid-deploy.
NOTHING WAS DELETED. The other nine keep their names, and eight of them
because their dates are true.
THE NINTH IS STILL WRONG AND IS LEFT THAT WAY, recorded rather than
quietly fixed: docker-compose.prod.yml.bak-20260807-162246 names
2026-08-07 16:22:46 and has an mtime of 2026-08-06 11:27 — a day out.
It is the oldest file in the set and predates any `cp -p` discipline, so
which of the two is the content date cannot be established from the host
alone. A rename would assert an answer nobody has. FOUR files were
mis-named, not three.
THE RULE THIS BOUGHT is OPS RULE 6 in docker/README.md: a backup is
named <file>.bak.of-<YYYY-MM-DD> from the SOURCE file's mtime, with
`cp -pn`, so the name and the timestamp agree and a second copy of the
same bytes is refused rather than duplicated. Every prescribed backup
command in the published docs now uses that one form.

     D1 INCIDENT SUMMARY — FR-01, the question "sensor fehler",
        2026-08-26 07:23 UTC. Retrieval returned 5 hits with a best
        score of 0.5651, which is above the similarity threshold, so the
        pipeline chose MODE A. The chat call then finished with
        finish_reason=length at the 1200-token cap, which raised
        ChatException, which surfaced as PROVIDER_UNAVAILABLE 503, which
        the UI rendered as "nicht erreichbar". THE SAME QUESTION AT
        10:45 UTC scored below 0.55, fell to MODE B, and succeeded.
        CLASS: a borderline retrieval and a vague question together
        produce the LONGEST answers; the token cap catches exactly
        those; and the failure is surfaced to the user as an outage.
        Three separate facts, and only the third is a lie to the user —
        the provider was reachable throughout.

     D2 PLANNED PULL REQUESTS, IN ORDER. Each is its own row because
        each has its own stop condition, and the order is not
        negotiable: nothing is calibrated before it is measured.
       (a) OBSERVABILITY, ZERO BEHAVIOUR CHANGE. A cause-carrying WARN
           at QueryService's catch site; a kind on ChatException so the
           cap is distinguishable from a real provider failure; log

           currently throw silently; and a request id issued by Caddy

       (b) TRUNCATION DEGRADES TO MODE B, with its own reason code, and

       (c) MEASURED CALIBRATION of the max-tokens ceiling FROM (a)'s

     A4 D1 AMENDMENT — HYPOTHESIS, 2026-08-26. The D1 entry above says
        the chat call "finished with finish_reason=length at the
        1200-token cap", and the natural reading of that sentence — a
        long answer that ran out of room — IS PROBABLY WRONG.
        WHAT THE MEASUREMENT SAYS: the incumbent, on this exact question,
        this exact machine and this exact retrieved set, REFUSES IN TEN
        TOKENS, six times of six, at 1200 and at 3000. It does not
        produce a long answer here at all.
        WHAT CARLOS READ IN THE PRODUCTION WARN: the content preview of
        the truncated body BEGAN WITH THE SAME REFUSAL, `{"claims": []`.
        Recorded as his reading of the production log; it is not in
        either measurement report and was not re-read here.
        THE HYPOTHESIS THOSE TWO FACTS SUGGEST: the 1200-token body was
        never a long answer. It is most plausibly a CONSTRAINED-DECODING
        DEGENERATION AFTER THE REFUSAL — under a strict json_schema the
        JSON whitespace between tokens is unbounded, so a model that has
        already emitted its empty claims list can run to the cap emitting
        nothing but padding. Stochastic at temperature 0.1, which is why
        the same question succeeded at 10:45 UTC and why six clean runs
        here did not reproduce it.
        LABELLED HYPOTHESIS ON PURPOSE. It is confirmed or killed by W-2,
        which logs the TAIL of a truncated body and its WHITESPACE RATIO
        — a ratio near 1 confirms it, a tail of real German kills it.
        Nothing downstream should treat it as settled before then.
        CONFIRMATION PATH, shipped by W-2 (#111) and usable from the
        first deploy: grep `chat truncated:` in the backend log.
          refusalShaped=true with whitespaceRatio > 0.9  -> CONFIRMED,
            the body is the refusal plus padding and W-3's degradation
            path is the fix.
          refusalShaped=false with a tail of German prose -> REFUTED,
            the answer genuinely ran out of room and the cap is the fix.
        The ratio is printed under the ROOT locale precisely so that
        `> 0.9` is greppable; see the defect the W-2 row records.
        UNTIL A REAL ONE IS LOGGED THIS STAYS A HYPOTHESIS. Six clean
        runs did not reproduce it, so the confirming line may take a
        while to appear — and its absence is not evidence either way.
        2026-08-26, AFTER W-3 (#112): THE INSTRUMENT AND THE
        DEGRADATION ARE BOTH LIVE, AND THE HYPOTHESIS IS STILL OPEN. W-2
        logs the anatomy and W-3 acts on the truncation, so a user no
        longer sees an outage either way — but nothing has yet confirmed
        WHICH shape production produces, because no `chat truncated:`
        line has been read. The degradation is deliberately identical for
        both shapes, so shipping it does not depend on the answer and
        does not settle it. `grep 'chat truncated:'` and, beside it now,
        `grep 'degrading to Mode B'`, whose classification word is the
        same evidence at the point where it changed the outcome.
        THE CONSEQUENCE IF IT HOLDS, and this is why it is worth writing
        down before it is proven: THE FIX IS A DEGRADATION PATH, NOT A
        BIGGER CAP. A cap of 2100 buys a degenerating answer 900 more
        tokens of whitespace and still fails. R1's cap change serves the
        FALLBACK MODEL, which genuinely needs the room; it is not a fix
        for D1 and must not be recorded as one.

GIT WORKFLOW (MANDATORY FOR EVERY AI SESSION — no exceptions)
=====================================================================
- Work on exactly ONE branch, created from up-to-date main:
    git checkout main && git pull && git checkout -b <type>/<short-name>
  Never create additional branches. Never commit or push to main
  (branch protection rejects it anyway).
- Commit in small logical units as you work, not one commit at the end.
- Conventional Commits: type(scope): imperative summary, max 72 chars.
  Types: feat, fix, chore, docs, ci, test, refactor.
  Scopes: backend, frontend, docker, docs, ci.
  Body (wrapped ~72 chars) explaining WHY when not self-evident.
  Never mention AI, Claude, or "generated" in commit messages.
- Before finishing: run `git log --oneline main..HEAD`, show the list,
  reword anything vague (no "update files", no "changes").
- Push the branch and open the pull request yourself:
    gh pr create --base main --title "<conventional title>" \
      --body "<markdown: What / Why / Verification / Out of scope>"
- Print the PR URL as final output. NEVER merge — merging is done
  manually by Carlos after review.
- After every merge Carlos refreshes local main with
  `git fetch && git reset --hard origin/main` (squash merges — never
  plain `git pull` after a merge).
