error dispatch, so the guard tests passed twice while production
refused. The replacement runs on RANDOM_PORT against a real Tomcat with
the JDK HTTP client, following no redirects.

- OPS RULE 3 (learned 2026-08-08, cost one failed deploy round): the
  prod compose bind-mounts the Caddyfile as a SINGLE FILE
  (./caddy/Caddyfile:/etc/caddy/Caddyfile:ro), and a single-file bind
  mount tracks the file's INODE, not its path. Replacing the host file
  with `mv` gives it a NEW inode, and the container keeps reading the
  OLD one. Nothing reports this: `caddy validate` and `caddy reload`
  run INSIDE the container and both happily operate on the stale
  content, and the reload reports success. Measured: a grep inside the
  container found 0 CSP lines while the host file had 2. REMEDY: `cp`
  OVER the existing file (same inode), or
  `up -d --force-recreate caddy`. Never `mv`. The same trap applies to
  any single-file bind mount — frontend-config.json is the other one
  in this stack. DOCS DEBT: DONE — arc42 §7.4, next to the .env rule.

UNIFIED REQUIRED CHECK — "build-and-test"
Branch protection requires exactly ONE status check name:

    build-and-test

Three workflows gate pull requests, and all three name their job
`build-and-test` (job id, no `name:` key — the id is what GitHub reports).
Whichever part of the repo a PR touches, a job under that name reports on
it. A PR touching two areas gets two checks under the name; both must pass.

The pull_request path lists are a PARTITION and are maintained as a set:

    frontend-ci.yml    paths:        frontend/**
                                     .github/workflows/frontend-ci.yml
    docs-pr-check.yml  paths:        docs/**
                                     .github/workflows/docs.yml
                                     .github/workflows/docs-pr-check.yml
    backend-ci.yml     paths-ignore: frontend/**
                                     docs/**
                                     .github/workflows/docs.yml
                       => catch-all: backend/**, docker/**, spike/**,
                          README.md, .gitignore, AI-USAGE.md, LICENSE,
                          everything else

INVARIANT — do not break this:
- A path may be ignored by backend-ci.yml ONLY if another workflow gives
  that PR a build-and-test check. A path ignored by all three leaves its
  PRs with no required check and permanently unmergeable.
- Root files (README.md, .gitignore, AI-USAGE.md, LICENSE) stay with
  backend-ci on purpose: they live outside docs/, so the docs build never
  reads them and would gate them on nothing.
- The gate workflows' own files (frontend-ci.yml, docs-pr-check.yml) are
  deliberately NOT ignored by backend-ci.yml, so editing a gate runs the
  backend suite too. Getting these lists wrong is how the repo loses its
  ability to merge.
- push triggers are NOT a partition: they exist to produce artifacts and
  fire the deploy workflows, so they stay narrow (backend-ci on
  backend/**, frontend-ci on frontend/**). Widening them would publish a
  new image for a README typo.

PIPELINE ARCHITECTURE (.github/workflows/)
1. frontend-ci.yml    PR (paths frontend/**) + push main: job
                      build-and-test — test with coverage (test runner:
                      vitest in jsdom — no browser needed on the runner),
                      build; upload coverage + Compodoc artifacts on main
2. backend-ci.yml     PR (catch-all, see partition above) + push main
                      (paths backend/**): job build-and-test — mvn verify
                      (JUnit + JaCoCo), OpenAPI spec; upload artifacts
                      on main
2b. docs-pr-check.yml PR (paths docs/** + the docs workflow files): job
                      build-and-test — renders the mermaid diagrams, builds
                      the site with build-docs.sh and link-checks it with
                      lychee. Publishes nothing.
3. frontend-deploy.yml / backend-deploy.yml
                      workflow_run success of the matching CI on main,
                      or manual workflow_dispatch for a redeploy without
                      a code change. Two jobs:
                        image  - multi-arch docker build (amd64+arm64)
                                 -> GHCR, tags :latest and :sha-<commit>
                        deploy - ssh to the Hetzner host as the deploy
                                 user, `compose pull <svc> && up -d <svc>`,
                                 then verify over the PUBLIC url (so DNS,
                                 TLS and Caddy are exercised too) and fail
                                 the job if it does not come back healthy
                      Both deploy jobs share the concurrency group
                      "hetzner-deploy" with cancel-in-progress: false, so
                      rollouts to the server serialise and a superseded
                      build never cancels one in flight.
                      Secrets (repo level): DEPLOY_SSH_KEY, DEPLOY_HOST,
                      DEPLOY_USER. The key is a dedicated ed25519 pair
                      used by CI only; it is passed through the step env,
                      never interpolated into a command line, and removed
                      in an always() step.
4. docs.yml           a) push main paths docs/**: regenerate mermaid
                         diagrams, build the site with Pandoc via
                         .github/scripts/docs/build-docs.sh -> gh-pages
                         (theme: docs/_theme, landing + arc42 + ADRs)
                      b) workflow_run success of frontend-ci/backend-ci:
                         publish coverage + API docs into gh-pages
                         subfolders (/frontend/coverage, /frontend/
                         api-docs, /backend/coverage, /backend/api-docs)
                         WITHOUT deleting the rest (keep_files)
5. release.yml        tag v*: GitHub Release with generated notes
